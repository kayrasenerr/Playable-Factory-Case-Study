## Actual limitations/corrections from this research session

These are factual examples from preparation, not invented future mistakes:

- A text-only web fetch could not inspect the three interactive exports. Instead of pretending to have played them, the kit records exact manual URLs and a direct-observation protocol. It cannot be reported as a completed user gameplay review.
- The source spreadsheet PDF split identity columns and performance columns onto separate pages. The preparation combined them by row order and visually checked both pages before calculation, avoiding a mistaken sixteen-row dataset.
- The product named Insight in the brief was not verified at the `/insight` public URL, which returned 404. The kit avoids assuming equivalence to Data and recommends the directly documented Ready product.
- Initial search coverage included irrelevant “Ready” results. The research narrowed to official PF product URLs instead of using unrelated results as evidence.
- Product pages already describe A/B testing and customization. The recommended proposal therefore specifies a more detailed goal/measurement/QA workflow rather than claiming basic A/B tests are new.

Use only examples relevant to the actual final workflow and preserve supporting prompt evidence. “The AI hallucinated X” is not appropriate unless it actually did so; a retrieval limitation or weak initial suggestion can be described accurately without exaggeration.

## Compact final language

Use concrete verbs: “ChatGPT organized the funnel; I checked the original eight rows and rejected an unweighted average” is informative only if the user actually checked it. If checking was done by AI/code, say that. Distinguish AI-generated code, deterministic calculations and human review rather than treating them as interchangeable proof.
