# Delivery, presentation and final verification

## Recommended output architecture

One coherent PDF/deck. Suggested allocation below is an editorial choice; the manual only imposes specific caps.

| Section | Suggested pages/slides | Limit to respect |
|---|---:|---|
| Cover | 1 | No stated cap |
| Task 1 | 8 | Maximum 8 for both companies combined |
| Task 2 | 1 | One-page proposal |
| Task 3.1 | 3 | Exactly three improvements per playable |
| Task 3.2 | 1 | Adapted flow of 3–5 steps |
| Task 4 | 1–2 | Text only; three banners |
| Task 5.1 | 2–3 | All required fields for ten prospects |
| Task 5.2 | 2 | One page per client in this recommended plan |
| Task 5.3 | Half page | Half-page maximum; can share a page with references or whitespace |
| Task 5.4 | 1 | One page |
| Sources | As needed | Keep readable; do not use appendix to evade task caps |

Use the task/subtask labels in headings. Each analytical page should lead with a conclusion, show the smallest amount of evidence necessary, distinguish uncertainty and finish with the decision/action. Client-facing means useful and intelligible, not unsupported confidence.

## Source integration

Use readable numbered source footers or hyperlinks, with a consolidated source section. For campaign results cite the supplied dataset and calculation method. Give full current evidence for final prospects; the seed sources in this folder are not a substitute for UA proof. Keep app IDs, ad IDs and screenshots in a linked evidence ledger where needed.

## Fact and content QA

- Every numbered subtask has an answer.
- Gaming and non-gaming coverage is explicit throughout; 3.1 evaluates the required gaming artifacts and 3.2 supplies the non-game adaptation.
- Task 1 has two clients, one concept and an actual visible mockup.
- Task 2 selects one allowed product and distinguishes existing functionality from the proposed extension.
- Task 3 contains nine evidence-backed changes, not generic assumptions.
- Task 4 contains three genuine banners with both client types.
- Task 5.1 has five qualified studios, five distinct non-game companies in one vertical, and all required fields.
- Task 5.2 has two separate client reports, selected/omitted metric rationale, missing in-playable metrics and 2–3 closing recommendations each.
- Task 5.3 includes prompts, data, identity matching, people, QA and limits within half a page.
- Task 5.4 reports real tools, real corrections, prompt evidence and actual non-AI choices.

## Numerical QA

Re-run `data/recalculate.py`; check totals against S02. Confirm the correct geo/OS row alignment, weighted ratio aggregation, money units, rounding and conversion names. Do not show invented revenue, ROAS, retention or calendar period. Do not label aggregate correlations as causal effects. Separate in-playable instrumentation from app events.

## Visual QA

Export then inspect every page at normal viewing size. Check clipped text, unreadable tables, dense source footers, inconsistent task numbering, and whether 5.3 actually fits half a page. Make the wireframe comprehensible without the linked prototype. Use consistent units and colors for gaming and grocery outcomes without implying they are directly comparable.

## Link QA

Open all user-facing links while signed out or in a permission-independent view where feasible. Use view-only sharing. The manual requests anyone-with-link access, but that is a setting to verify, not something an AI can claim automatically. If it cannot set/check permissions, list the exact links and remaining action. Do not send the submission or contact prospects without separate user instruction.

## Final handoff statement

Deliver the main PDF/deck, supporting evidence/AI links and a brief list of any unresolved checks. Do not call a draft “ready to submit” if playable inspection, prospect qualification or AI log evidence remains missing. If a source is blocked, identify the affected claim and the smallest evidence needed; complete all unaffected work.
